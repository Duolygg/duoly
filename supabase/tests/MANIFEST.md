## Public teammate profiles

`public_teammate_profiles.sql` runs against the disposable latest-schema database only. It covers opt-in publishing, privacy allowlists, rating and win-rate minimums, index quality, slug validation and reservation, rename/history, admin ranks and moderation, suspension, RLS and the review notice cutoff. It retains the canonical first-statement guard and rolls back every fixture. The suite prints its actual assertion count.

`public_profiles_default_on.sql` covers the default-on release. It asserts the review notice cutoff set at apply time, slug generation from display names (Latin accents, reserved words, duplicate names, slugs retired inside 90 days, scripts the rules cannot carry, the 24 character cap), the backfill over every active teammate with an approved game, the access trigger (a first approved game creates the page, losing the featured game moves it, losing the last game unpublishes without dropping the slug), the featured-game write guard that replaced the row check, the three-way indexing rule, and booking a named teammate through favorites including the queue delay the profile copy promises. It retains the canonical first-statement guard, rolls back every fixture and prints its assertion count.

## Restored directly affected Discord coverage

The manifest now runs 38 entries covering 46 SQL files. It excludes 33 executable files: 20 SQL files and 13 builders/non-SQL harnesses. These are inventory counts, not passing-test claims; exact-head execution evidence is recorded on draft PR #222 after the run completes.

`background_switches.sql` is the event-driven background build's suite (20261112140000). It asserts that the migration left `duoly-dispatch` active and the fixer unscheduled, that all four kinds default to `shadow`, that the orders trigger registers `order-post` at queued_at + 100 s and `order-expire` at queued_at + 5 min with the key's epoch, that the registration carries a body-bound HMAC and never a bearer, that a half-configured Vault skips in silence, that `duoly_dispatch` skips only `live` kinds and fails safe towards the legacy owner, and that `background_finalize` refuses until every kind is live while `background_rollback` is idempotent. The pgcrypto known-answer vector pins SQL signing to the Web Crypto helper in `src/contracts/background.ts`.

`discord_order_posts.sql` and `discord_role_sync.sql` change only their obsolete scheduling expectations: original jobs and the old Discord pruner remain present but paused, the shared dispatcher is active at ten seconds, and the hourly global prune uses the 24-hour terminal cutoff and 50,000-row bound. All post due/claim/save/failure/retry/close, handover, facts, authorization and unlink assertions remain unchanged. No other legacy exclusions were ported.

The targeted integration review covers the interim dispatcher and disposable runner/workflow only, not a timer cutover. Existing 10/20/30/60-second **minimum** call intervals remain hard bounds before predicate fail-open. A ten-second scheduler is not a maximum latency guarantee: because state records actual enqueue time, a scheduler tick arriving just short of the minimum is skipped, and work waits for a later tick. Do not subtract jitter tolerance from the gate; that would weaken the rate caps. External Discord drift still receives the unconditional ten-minute fallback and age-based membership refresh.

Rollout remains owner-gated on actual cron ownership, retained payments timeout/command and effective pg_net queue ACLs. Reusing narrow bearer credentials in pg_net does not solve the pre-existing readable-queue credential risk; no service-role credential is introduced. SQL CI has only fake, rolled-back credentials and blocks DB-container egress. Local test success neither verifies hosted ACLs nor authorizes rollout.
