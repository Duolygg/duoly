# Proof implementation interface lock

Implementation decisions for the independent upload/read slice in proof-completion-contract.md. These are transport and operational choices, not invented completion or financial rules. No completion, payment, earning, wallet, dispute or payout mutation.

## DTO and RPC names

`Proof = { id: UUID, order_id: UUID, assignment_id: UUID, mime: 'image/png' | 'image/jpeg' | 'image/webp', byte_size: positive integer <= 1572864, created_at: ISO timestamp }`. Strict DTO, no uploader, locator, digest, filename or history identity. Lists return `{ proofs: Proof[] }`; upload and finalization return `{ proof: Proof }`.

- Authenticated `authorize_order_proof_upload(p_order_id uuid, p_assignment_id uuid)` returns strict `{ order_id, assignment_id }`. This is a side-effect-free preflight: derive fresh auth.uid/role/access and current open in-progress assignment under a brief order SHARE lock, with no sweep, reservation, refund or other mutation. HTTP must call and validate this before checking storage availability or reading upload bytes. Do not reuse `teammate_current_assignment`: its unrelated expiry sweep would violate proof isolation.
- Authenticated `begin_order_proof_upload(p_order_id uuid, p_assignment_id uuid, p_request_id uuid)` returns `{ id, order_id, assignment_id, state: 'pending' | 'ready' }`. Lock order before proof; validate current active teammate and access freshly. One reservation per assignment/request, maximum five pending plus ready. Repeating an abandoned request conflicts. Ready metadata is immutable.
- Service-only `finalize_order_proof_upload(p_proof_id uuid, p_mime text, p_byte_size integer, p_sha256 text)` returns `{ proof }`. Bind to original reservation actor and currently active assignment, recheck fresh role/access, enforce MIME/size/digest and existing object metadata. Repeating identical finalization is idempotent; different data conflicts. No client validation flags or actor parameters.
- Service-only `abandon_order_proof_upload(p_proof_id uuid)` returns `{ abandoned: boolean }`. Lock order then proof; never abandon ready data. A false result must not permit object deletion. Mark abandoned before compensating storage deletion. Ending an assignment abandons its pending reservations via a private trigger, retaining ready historical evidence.
- Authenticated `list_order_proofs(p_order_id uuid)` returns `{ proofs }`. Owner customer and admin may inspect retained historical proof; teammate sees only own current assignment and no former/replacement evidence. Denied reads use PT404. Metadata escalation cannot change role.
- Authenticated `get_order_proof(p_order_id uuid, p_proof_id uuid)` returns `{ proof }` with the same per-request authorization and exact order/proof pairing.
- Service-only `claim_stale_order_proof_uploads(p_limit integer default 100)` returns `{ proofs: [{ id, order_id, assignment_id }] }` for abandoned and pending reservations older than one hour, marking pending abandoned under consistent order/proof locks. Never return ready rows. Repeated claims permit retryable cleanup. One hour is a conservative operational reservation timeout, not a product completion deadline. Parent must wire and verify trusted cleanup before uploads are enabled on hosting. Feature defaults off until then; no bare public cleanup endpoint.

## Storage

Private bucket `order-proof`, file limit 1572864 and only the three adopted MIME types. Storage key is computed exclusively by server as `${order_id}/${assignment_id}/${id}` with no extension or caller path. Add a restrictive storage.objects policy denying this bucket to anon/authenticated even if other permissive policies later exist. No raw proof-table grants to anon/authenticated/service_role; expose narrow functions only. RLS enabled. Default PostgreSQL owner remains migration/maintenance authority. Server-only service credential is `SUPABASE_SERVICE_ROLE_KEY`, never serialized or exposed to client config. Missing/disabled storage returns safe unavailable, never a mock success.

## HTTP

- `POST /api/teammate/orders/:id/proof` accepts one raw image. Headers: `Content-Type`, `X-CSRF-Token`, `X-Assignment-Id`, `X-Idempotency-Key` (last two UUIDs). Require same origin, existing CSRF cookie verification, fresh teammate identity, and pre-read assignment ownership through authorized order read; stream-bound body independently of Content-Length. Do not change the existing 4096-byte JSON/form cap. Validate type/magic/size before begin/storage. No filenames, external URLs, arbitrary keys or bulk envelope.
- Storage upload uses upsert false. On duplicate or ambiguous object-write acknowledgement, download and validate exact stored bytes/digest before finalization; different bytes with the same key conflict. Never overwrite or abandon another concurrent matching upload simply because the object already exists. Failed finalization compensates only after a successful abandon; ready objects must never be deleted by a racing loser.
- `GET /api/orders/:id/proof` lists. `GET /api/orders/:id/proof/:proofId` independently authorizes and proxies bounded bytes, never a signed/public URL. Validate storage bytes against ready MIME/size/digest as feasible. A read failing participant/order/proof checks returns404, including anonymous images. Infrastructure failures return503 without internals. All responses private/no-store; bytes also nosniff and exact MIME.
- `ORDER_PROOFS_ENABLED=true` gates deployed upload/storage use; default false. It does not disable existing order features. Test injection may supply an explicit scoped adapter, never a fake production fallback. Parent enables only after actual SQL/storage/HTTP and cleanup acceptance.

No edits to established order response shapes, acceptance/reroll money semantics or existing JSON body limits. UI follows after this checkpoint is committed, preserving the existing design.
