## Useful behavior retained and gaps that must not survive

### F01 — CRITICAL

paid, tip and Paid are local records, not payment collection, confirmed tips or actual payouts. placeOrder trusts browser total/category/title.

**Required:** Server-owned quote and verified payment webhook; immutable payment and payout events with idempotency, reconciliation and explicit live-money enablement.

Evidence: `lib/orders.js`, `app/api/orders/route.js`, `lib/ledger.js`, `lib/payouts.js`.

### F02 — CRITICAL

accept checks queued status before awaiting accessOf; overlapping calls can both pass then overwrite assignment. Other completion/review/report/wallet operations have await gaps; process globals do not provide cross-instance consistency.

**Required:** Database transaction/row locking and conditional state updates, unique active assignment/open-customer order/event keys; concurrency tests.

Evidence: `lib/orders.js`.

### F03 — HIGH

JSON/global stores and queued save promises acknowledge before durable commit and may log write failure while returning success. Several loaders recover corrupt files as empty.

**Required:** Do not import store implementation into runtime. Postgres transactions/RLS/backup/restore, private object storage, durable outbox and clear failure semantics.

Evidence: `lib/orders.js`, `lib/roles.js`, `lib/ledger.js`, `lib/payouts.js`, `lib/support.js`.

### F04 — HIGH

Audit recording is a separate admin POST; operational services do not automatically append it. Brief demand every admin action is not actually guaranteed by source.

**Required:** Write authenticated actor/action/detail in same transaction as every privileged mutation, never rely on UI follow-up.

Evidence: `lib/audit.js`, `app/api/admin/audit/route.js`, `app/api/admin/orders/route.js`.

### F05 — HIGH

Deposits release on elapsed time only, not absence of dispute. Report approval records €50 owed but has no bounty payout/credit implementation.

**Required:** Dispute hold entity and release eligibility; explicit one-time bounty liability and reviewed settlement path.

Evidence: `lib/ledger.js`, `lib/payouts.js`, `lib/reports.js`.

### F06 — HIGH

Friday grouping uses server-local timezone and fixed 7-day milliseconds; late review tips mutate entries in original completion week, potentially changing Paid totals.

**Required:** Explicit Europe/Vienna civil-week semantics with DST tests; separate tip/adjustment events by settlement date and immutable paid statements.

Evidence: `lib/payouts.js`, `lib/ledger.js`.

### F07 — HIGH

Wrong-game claim GET returns order payload with blocked reason; game-toggle filter affects presence/misses, not deskState queue; Discord queue embeds disclose auto-cancel deadline to teammates.

**Required:** Approved server visibility policy wins over source leaks; redact blocked claim entirely, consistently enforce queue game preferences and remove timing from teammate notifications.

Evidence: `app/api/claim/[token]/route.js`, `app/api/desk/route.js`, `lib/orders.js`, `lib/discordQueue.js`.

### F08 — MEDIUM

Catalog has 15 games/162 normalized services and 45 bundle names; learn half-price is unconditional source catalog pricing. Wingman ladder minimum .75 is an exception to brief approximate .8 range.

**Required:** Retain exact catalog/ranks, apply first-session entitlement on server to only one eligible session, validate rank rather than silent fallback; retain Teams content but disable unsupported multi-seat fulfillment.

Evidence: `lib/catalog.js`, `lib/ranks.js`, `lib/orders.js`.

### F09 — MEDIUM

FAQ markets PRO membership and favourites/direct rebooking, trust perk labels imply automatic matching perks, and creator calculator describes unimplemented attribution. Legal text promises provider/retention behavior not established by implementation.

**Required:** Preserve as source evidence, not feature claims. Approved brief is target; user email+password Supabase overrides OTP. Remove unsupported claims before launch and verify legal/merchant facts.

Evidence: `lib/faq.js`, `lib/creators.js`, `lib/trust.js`, `lib/legal.js`.

### F10 — HIGH

Magic/size checks and filename restrictions are useful, but avatar dimensions rely on browser, upload URL ownership is not checked by profile regex, and body sizes are not bounded before base64 decode.

**Required:** Server re-encode/size/dimension quotas, storage object ownership binding, rollback/outbox cleanup, private evidence ACLs, no-store evidence serving.

Evidence: `lib/avatars.js`, `lib/roles.js`, `lib/uploads.js`.

### F11 — MEDIUM

ledger comment claims orders are trimmed to400 but actual orders.save keeps every order; wallet history recomputes cashback with creation-order/current constants rather than immutable earned postings.

**Required:** Use executable behavior not stale comments; persist policy/version and completion-ordered rewards, gifts and refund reversals in ledger.

Evidence: `lib/ledger.js`, `lib/orders.js`.

### F12 — HIGH

Source boot creates per-process timers and WebSocket worker; global singleton cannot prevent duplicate bots in multiple deployments or posts sent before persistence.

**Required:** Dedicated single-leased worker, durable scheduling/outbox/reconciliation; do not boot from Astro serverless routes or preview.

Evidence: `instrumentation.js`, `lib/discordBot.js`, `lib/discordQueue.js`.

## Dependency sequence (vertical slices, not separate backends per screen)

All stateful slices depend on fresh server identity and durable authorization. Pure catalog extraction can proceed in parallel, but cannot authorize a payment. Admin screens use the same commands as customer/teammate flows; they do not get independent money stores.

S1. **Identity/account foundation** — depends on none. Supabase email+password signup/login/confirmation/reset; OAuth configured separately; fresh server roles; owner immutability; no role from user metadata; account RLS tested on disposable DB.

S2. **Catalog and server quote** — depends on S1. 15 games/162 services retained; quantities/discounts, rank variants, first-session eligibility, mid/markup snapshots; no money moved; Teams disabled until seat model.

S3. **Durable transaction model and authorization** — depends on S1, S2. Tables/constraints/RLS for orders, assignments, payments/events, wallet postings/reservations, chat, access, ledger, payouts, reports, flags, applications, support, audit; private storage ACL; atomic commands and outbox.

S4. **Confirmed checkout -> paid order** — depends on S2, S3. Server-owned quote + actor/order limit + wallet reservation; signed webhook verifies amount/currency/provider intent; one event one order, retries recover; test mode only before live-money authorization.

S5. **Queue/presence/priority/claim** — depends on S3, S4. One atomic winner, one active assignment; authoritative deadlines even without viewers; expiry wallet credit once; visibility history/miss rules; private realtime with server projections; Discord-link eligibility.

S6. **Fulfillment/chat/proof/review/moderation** — depends on S5. Participant-only chat; filter before publish; proof ownership/limits; two 5-minute rerolls archive chat; completion+ledger+rewards transaction; review once; tip only on provider confirmation; report decision/bounty liability.

S7. **Earnings/wallet/trust/rewards/payout reconciliation** — depends on S3, S6. EUR/USD immutable postings; historical reward policy and no double gifts; dispute-aware 14-day release; explicit Friday Europe/Vienna boundaries; immutable settled payout rows; provider sandbox reconciliation before live payouts.

S8. **Applications and support/admin operations** — depends on S1, S3. Durable rate limiting; one pending application/open conversation; approval transaction; own-data Sparky; guest cookie isolation; every admin action audit; email delivery is independently configured/verified.

S9. **Discord singleton and notifications** — depends on S5, S6, S8. One leased worker outside serverless; durable outbox/dedupe; mock gateway/REST failure tests; explicit provider credentials/guild/permissions approved; disabled preview side effects.

S10. **Launch review and deferred extensions** — depends on S7, S8, S9. Real merchant/legal/contact and privacy facts; financial/legal approval; provider test-mode acceptance plus explicit live-money gate; creator tracking and multi-seat work remain separate, never silently inferred from old UI.

S8 can proceed alongside S4–S7 once S1/S3 exist. S9 needs the canonical queue/support contracts, not a second state machine. Do not start long-lived timers or a WebSocket bot in an Astro/Vercel request handler. Schedule authoritative queue expiry even with no open browser; keep a pre-command expiry check to eliminate deadline races. Use Supabase Free-compatible primitives and an explicitly approved worker host rather than assuming paid features.

### Visibility is part of the API contract

- Customer sees own complete order, proof/review/tip and teammate public snapshot. Original `customerView` is a deliberate DTO, not simply a raw store dump.
- Teammate queue/active DTOs exclude customer id/payment totals/method, private proof/review/tip/history/ignoredBy; queued DTO also hides age/auto-cancel timing. Never expose priority or hidden-order counts via HTTP, realtime, notifications or Sparky. Re-rolled orders look fresh.
- Only current customer/assigned teammate/admin may fetch **proof**. Only reporter/admin may fetch **report evidence**; accused teammate does not get that evidence merely by participating in the order. All denies are404, private files `no-store`; avatars intentionally public.
- Chat GET may remain readable for current participants after completion; POST only `in_progress`. Last200, max500 chars, typing4s, max20/min; filter rejects before delivery and records admin flag. Rerolled old participants lose current chat access; archived old chats are protected administrative evidence.
- Admin list emails should be masked in DTOs, not only visually. Source mask helper does not prevent full email bytes from reaching an authorized admin browser.

## Money and durable data contract

Use distinct immutable, currency-specific postings for customer EUR wallet, payment intents/events, teammate USD earnings/deposits/tips, payout statements/settlements, adjustments, report-bounty liabilities and any future creator commission. Refund-to-wallet and provider refund are different operations. Wallet spending first must reserve/debit credit exactly once alongside checkout; failed/expired checkout releases reservation. A cancelled order refunds the full EUR price including its original wallet portion **without** double crediting that portion. A completed admin-refunded order leaves teammate pay intact but reverses customer cashback/qualifying count/gifts as the approved reward policy requires.

Source payout formula is `max(0.99, round(amountEur * 0.6 * eurToUsd, 2) - 0.01)` USD, stored with booking FX. Customer USD uses mid+1%; earnings and tips use mid. Preserve exact source ladder exception Wingman×0.75 and half-step `.49/.99` rank rounding; do not replace source prices with approximate values. Keep event FX and monetary minor units stable; source live-rate conversion and floating-point history recomputation are evidence, not the durable accounting design.

Trust thresholds0/100/250/500/1000 deposit10/8/5/3/0%, held14days without dispute. Customer levels0/100/250/500/1000 cashback1/2/3/5/7%, gifts€0/5/15/40/100; cashback uses level before the qualifying completed order, gifts once, refunded orders do not qualify. Source wallet calculation uses creation order, not completion chronology; immutable earned-policy events must fix this. Friday payout weeks need an explicit Europe/Vienna civil-time policy and DST tests, never host-default timezone.

The minimum durable model covers accounts/verified identities/roles/profiles/preferences/access, orders/assignments/transitions/chat/visibility events/claims/Discord-post keys, payments/webhook events/quotes/wallet reservations/postings, earnings/deposits/disputes/reviews/tips/payout statements/settlements/adjustments/reward awards, moderation flags/reports/evidence/bounties, applications, support conversations/messages/guest capabilities, audit entries and notification outbox. Object storage rows bind uploaded files to owner/order/report. Explicit constraints, grants and RLS must be exercised against a disposable database before exposing any product records. Neither this inventory nor the source data is a migration of real funds.
