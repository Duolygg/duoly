## Exact adopted product behavior

### Ownership, completion and administrative restrictions

1. Only the **assigned teammate** can complete an **in-progress** order, submitting **1–5 valid screenshots**. No customer confirmation, elapsed-play minimum or automatic completion is specified. Completion records server completion time and proof, then an earning; it closes chat writes and emits the completion system message. Customer rating follows completion rather than causing it (B **Orders (the core)** lines 44–48,53; O:`lib/orders.js:253–267,275–294,657–662`). Do not add a customer-approval gate.
2. Server-side role checks are required on every request. Admins **never play orders**: they cannot accept, upload as the playing teammate, or complete, even if they know IDs or hold a handover token. They may inspect private proof and later route/cancel/refund via separately authorized APIs. Customer and teammate accounts cannot invoke admin operations (B **Roles & auth** lines 13–15; **Orders (the core)** lines 45,50; O:`app/api/orders/[id]/route.js:26–38`; O:`lib/orders.js:223–250,349–354`). Owner email/admin invariants are not replaced by a test-email bootstrap.
3. Acceptance remains existing server authorization: teammate role, verified linked Discord, not suspended, eligible game/GG class, released priority unless a legitimate handover, not own order, not already active; first accept wins. Proof endpoints must not provide a new acceptance or priority bypass (B **Orders (the core)** lines 39–45; M:141–152,290–320). Revalidate ownership after asynchronous storage work, not only before it.
4. Admins cannot suspend someone or change their role mid-order (B **Admin panel (`/admin`)** line 74). Future role/access administration must preserve that constraint. Reads still use current DB identity, never client/provider metadata (C:`docs/product/order-foundation-contract.md:8`; C:`supabase/migrations/20261021230000_account_foundation.sql:44–60,95–115`).

### Assignment and reroll-history isolation

- Customer may reroll at most twice, only during the first five minutes after current accept. Queue timer restarts; previous teammate cannot return through the queue, only through a future genuine admin handover. Old chat is archived and the new teammate starts fresh (B **Orders (the core)** lines 47,50–51; O:`lib/orders.js:297–325`; M:339–353).
- Bind each staged proof to the immutable **assignment UUID**, order UUID and uploader, not merely order ID or teammate ID. An upload started before reroll must never attach to the replacement assignment. Prior teammate loses write/read access to the new assignment immediately; replacement receives neither old proof nor old chat/history metadata. Historic proof must remain distinguishable internally for customer/admin investigation, not be silently reassigned to the replacement.
- The historical source had no pre-completion staging: files were attached only by completion. Retaining assignment-scoped staged evidence for customer/admin inspection is the proposed secure adaptation, not an assertion that the old UI did this. Generic queue DTOs must reveal no evidence count, storage path, old assignment, reroll count or old teammate. An actor may know their own current assignment ID without receiving history (M:130–139; C:`src/contracts/orders.ts:58–66`).
- Reports are **separate evidence**. Customer reports target current or last teammate; types `off_platform`/`toxic`, text ≥10 characters, 1–5 screenshots, one per type per order. Approved report owes €50 bounty; source only records the decision, not a wallet/payment posting. Accused teammate cannot read report evidence merely because they may read completion proof (B **Orders (the core)** line 49; O:`lib/orders.js:328–346`; O:`lib/reports.js:8–12,26–31,41–60`). Do not merge report ACL into proof ACL.

### Earnings, security deposit and loyalty — preserved facts

- Booking owns EUR amount, booking FX and USD payout. Brief formula is `max(0.99, round(amountEur × 0.6 × eurToUsd, 2) − 0.01)`; platform fee 40%, teammate share 60%. Completion consumes the **stored payout**, never the browser amount or current FX (B **Catalog & pricing** lines 29–30; O:`lib/orders.js:423–424`; O:`lib/ledger.js:26–38`; M:23–25).
- One permanent USD earning per completed order; unique order identity prevents duplicates. Source chooses teammate trust tier using **completed entries before this order**, rounds payout to two decimals, computes `held = round2(payout * depositPct / 100)` and `net = round2(payout - held)`, initializes tip 0, rating null, tags/text empty, with completion timestamp (B **Money** lines 60–61; O:`lib/ledger.js:24–40`). Future SQL uses integer minor units/exact numeric arithmetic, not binary-floating client inputs.
- Trust thresholds/deposit: Rookie 0/10%, Trusted 100/8%, Veteran 250/5%, Elite 500/3%, Legend 1000/0%. Held deposit releases after **14 days without a dispute**, not an unconditional timer (B **Money** line 61; O:`lib/trust.js:4–16`). No release, payable-week generation or payout action is enabled in this slice.
- EUR wallet is refunds + cashback + level gifts + admin adjustments − wallet spent, never negative, never expires. Loyalty completed-order thresholds/cashback/gifts: Bronze 0/1%/no gift; Silver 100/2%/€5; Gold 250/3%/€15; Platinum 500/5%/€40; Diamond 1000/7%/€100. Cashback uses the customer's level **before** the completion; threshold-crossing order uses old rate and then reaches new level/gift. Refunded orders earn nothing and do not count (B **Money** lines 57–58; O:`lib/rewards.js:4–20`; O:`lib/orders.js:523–545`).
- Reviews are later: completed only, once, 1–5 stars, 500-character text, up to four allowed tags, optional 0–100 tip. Tips go 100% to teammate, converted at mid FX; actual charging is not built. Never post source's uncharged client tip as an earning. Source converts non-USD tip with current FX at review time; durable trusted-tip FX/payment provenance needs its own contract (B **Orders (the core)** line 48; **Catalog & pricing** line 29; O:`lib/orders.js:271–294`; O:`lib/ledger.js:43–53`).

## Minimal next vertical slice: private staged proof upload and read

The following names/shapes are **proposed interfaces**, not claims that RPCs/endpoints already exist. This slice is usable against existing valid development orders and requires no creation endpoint. If development has no active orders, demonstrate with rollback-only authorized database fixtures; do not manufacture paid orders through application APIs.

### SQL boundary

1. Add private `order_proof_uploads` metadata with opaque UUID, order/assignment/uploader binding, server-generated storage key, detected MIME, decoded byte count, lifecycle (`pending`, `ready`, `abandoned`), timestamps and idempotency key. Enforce composite assignment ownership FK and unique key; reject arbitrary object URLs/keys from clients. Ready metadata is immutable. No anon/authenticated table access or realtime publication; explicitly revoke default grants, enable RLS.
2. Proposed user-scoped `begin_order_proof_upload(p_order_id,p_assignment_id,p_request_id)` derives `auth.uid()`, checks fresh teammate role and current active ownership under the order lock, reserves one slot, returns only opaque proof/upload IDs. Count pending + ready reservations under the same lock, cap at five for the assignment, make retry idempotent. No caller actor, role, time, price, MIME-trust or bypass parameters.
3. Raw bytes are accepted only through trusted HTTP storage adapter, which validates size/MIME/magic. A service-only finalizer stores **validated** metadata and transitions pending → ready after checking the same active assignment under lock. It is not an authenticated-client RPC accepting a self-asserted “validated” flag. Reservation records bind the initiating actor; a service token cannot substitute a caller-chosen uploader.
4. On reroll, abandon outstanding reservations for that assignment transactionally; any asynchronous finalize then fails without attaching. Retain ready objects as assignment-isolated private evidence, visible to customer/admin only after reroll, not former/replacement teammates. Implement logical exclusion immediately; perform physical orphan cleanup via trusted compensator without exposing deletion to clients. Cleanup cadence/retention for staging is **N/R**; document deployment choice before enabling unbounded uploads.
5. Proposed list/read-authorization RPCs return opaque ready proof IDs, MIME, byte count and assignment-local context only to permitted participants. Internal storage locator is available only to the server adapter after an authorization check, never general DTOs. For historical proof the assigned teammate may read their completed final assignment while they remain a teammate; rerolled-out teammate is denied. Admin fresh role permits investigation, not mutation-as-player.
6. Helpers use qualified names/empty `search_path`; grants separate authenticated authorization RPCs from service-only byte-finalization/storage operations. No direct inserts/updates of proof/order/ledger by browser, and no storage membership based solely on a path prefix or self-selected user ID.

### Storage and HTTP boundary

- Private storage bucket/object namespace; deny public listing/read/write and ordinary direct storage operations. Server-only storage credentials stay server-only; user-scoped SQL remains the source of caller authorization. Immutable keys prevent overwrite and cross-assignment reuse. Do not grant the entire application a generic proof-table bypass.
- Proposed `POST /api/teammate/orders/:id/proof` accepts assignment/idempotency identifiers plus one raw image per request. Require same-origin CSRF using existing cookie/token verification (header transport may be adapted explicitly), fresh session and teammate role **before** reading large data. Stream-bound decoded payload to the exact per-image maximum, independent of Content-Length; reject empty, oversized/chunked-overflow, unsupported MIME and magic mismatch before storing ready evidence. Do not trust browser compression, filename or Content-Type alone. One-at-a-time transport avoids inventing a bulk envelope limit; completion later selects 1–5 ready IDs.
- Return a strict opaque proof result only after byte write and successful SQL finalization. Retry same request ID reuses result/reservation, not new objects/slots. Storage failure cannot mark ready; finalization failure leaves no visible attachment and schedules/removes orphan bytes. Pending evidence is never readable. No state change or earning occurs on upload.
- Proposed `GET /api/orders/:id/proof` lists authorized evidence; `GET /api/orders/:id/proof/:proofId` authorizes **order + proof + assignment** on each request and proxies bytes, never redirects to a bearer/public URL. Anonymous image requests, guessed/malformed IDs, wrong order/proof pair, nonparticipant and removed teammate return 404 without a locator. Known authenticated mutation role/state failures may use existing 403/409 conventions; infrastructure failure is 503 with no internals.
- Read responses use exact detected MIME, `no-store`, `nosniff`; disable shared/CDN caching and exclude payload/locators from analytics/logging/errors. All metadata responses are private/no-store too. Do not return signed URLs: signing expiry remains **N/R**, not an invented TTL. Future signed access requires a separate revocation/expiry contract.
- Add real teammate upload/list/open UI and customer proof list/open UI, with count/size/type errors and reroll reset keyed by assignment ID, not order ID alone. Explicitly label uploaded evidence as **not yet completion**. Keep “complete” unavailable, not a button that pretends success or modifies browser-local order status.

### Later completion boundary (blocked, not part of upload/read delivery)

After the policy decisions above, a user-scoped `complete_order(order_id, assignment_id, ready_proof_ids, request_id)` must lock fresh actor/role and order, validate 1–5 distinct ready images all belonging to the current assignment, serialize teammate/customer progression, consume proof once, close assignment, set completed state/server time, and atomically post unique permanent USD earning/deposit and EUR loyalty/gift effects. No caller-supplied payout/deposit/FX/cashback/tip/rating/time. Retain immutable posting IDs and chosen pre-completion tiers/rates for audit. A retry returns the same committed outcome; posting failure rolls back completion. Lock ordering must be consistent with accept/reroll/refund to avoid deadlocks. No deposit release, real tip or provider payout is implied.

The future trusted payment producer creates eligible orders using server pricing, persisted booked FX/payout and verified payment provenance; proof/completion cannot create or assert payment. Existing development rows may exercise authorization/proof, but are not evidence of a charge. Payment-event deduplication/provenance is a separate contract, not invented here.

## Actual acceptance criteria for implementation

These are required executable checks, **not results claimed by this document**:

1. **Real role-switched SQL:** anonymous, no-subject, customer, unrelated teammate, assigned teammate, former teammate and admin. Deny raw proof/order/storage writes, helper execution and client finalization. Metadata role escalation fails. Admin can read, never upload/complete. Wrong-order/proof pairing reveals nothing.
2. **Actual bytes through HTTP/storage:** valid PNG/JPEG/WebP each opens only to allowed principals; invalid/empty/truncated magic, MIME mismatch, renamed nonimage, unsupported MIME, maximum+one byte and chunked overflow reject. Exact maximum accepted with valid magic; count five succeeds, sixth reservation fails; zero/six IDs cannot later complete. Test actual no-store/nosniff/MIME and lack of public storage URL/listing. Browser preprocessing is bypassed in negative cases.
3. **Two-session races:** simultaneous fifth/sixth slot reservations cannot exceed five; same idempotency key creates one object/result. Pause upload before finalize, reroll and accept replacement, resume: old finalize denied, new teammate sees no historical proof/count/chat/identity. Former teammate cannot open replacement evidence. Retry/lost acknowledgement does not consume extra slots.
4. **Failure integrity:** fail object write and SQL finalize separately; no ready row for missing object, no attached wrong-assignment bytes, orphan cleanup demonstrated with exact object/metadata readback. No completed_at/status, earning, deposit, cashback, gift or refund changes from upload/list/read failures or successes.
5. **Live session/HTTP authorization:** real session cookies, CSRF absent/wrong/origin mismatch, stale role/access and logout. Read image after switching browser accounts is denied (no cache reuse). Deny arbitrary key/URL/actor/time/price fields and unsupported methods; errors contain no internal locators or secrets.
6. **Regression:** existing queue eligibility/privacy, first-accept race, expiry/refund dedupe, customer ownership, reroll limit/window, strict DTO decoders and browser mobile/desktop flows remain green. No additional generic teammate order fields or raw-table realtime grants.
7. **Proof vertical demonstration:** assigned teammate uploads to an existing development assignment, customer and admin open privately, unrelated user is denied, and proof UI survives refresh. If no development assignment exists, use isolated/rollback-only fixtures and report that limitation honestly. Parent alone reviews/applies migrations and verifies storage policies/readback; no production writes.
8. **Full completion only after unblock:** actual concurrent completion/retry/reroll/cancel tests, next-order acceptance after completion (assignment index regression), unique earning/deposit/reward/gift postings, threshold tests and approved completed-refund/reward-spend/dispute cases. No “done” claim based solely on a status change or static SQL checks.
