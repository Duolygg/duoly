# Shared order foundation contract

Approved target: backend-rebuild-brief.md and original backend-salvage.json. This slice uses Supabase PostgreSQL, never JSON files/global state, and introduces no real payments or public paid-order creation.

## Scope and authority

- Postgres owns order state, eligibility, exclusive acceptance, queue deadlines, cancellation, reroll assignment history and refund credit postings. Realtime will publish authorized committed outcomes later; it never grants an assignment.
- Existing account_roles and profiles are the identity foundation. Read roles from the database on every command; never use user metadata. No owner/admin bootstrap is inferred from a test email.
- Ordinary clients cannot insert orders or edit financial/access/priority columns. There is NO public order-creation RPC or fake-paid endpoint. Future verified payment handling will be a separate trusted producer. Database tests may seed rollback-only fixtures explicitly as database owner.
- No Stripe connection, charge, payout, customer email, Discord post or new production database is part of this slice. Supabase stays Free. Parent alone applies approved migrations to development after review and rollback-only tests.

## Durable model

- Orders have stable UUID identity plus generated DL-<sequence> public reference; customer UUID; game/service/title; integer units1-10 and unit; GG marker; bounded rank/region/IGN/note/voice and public customer snapshot; integer EUR amount99..100000, trusted booking FX and USD payout; status queued/in_progress/completed/cancelled; queued/accepted/completed/cancelled timestamps; current assigned teammate and assignment ID; rerolls0..2; cancel reason. Financial inputs belong to a future server quote/payment producer.
- Unique partial constraints enforce one queued/in_progress order per customer and one in_progress order per teammate, independent of application races.
- Assignment history retains prior teammates and a distinct assignment UUID for future chat isolation. Reroll does not expose previous teammates or old chats to the next teammate.
- Trusted teammate access stores approved games/GG access, verified Discord identifier, suspension, admin-only priority base/adjustment/expiry. No client writes. Default access denies all.
- Refund credit postings are permanent EUR ledger events, positive, uniquely keyed by order and refund kind. Expiry or queued cancellation credits the full EUR amount exactly once. No wallet spending, cashback or real provider refunds yet. Clients cannot write postings.

## RPC boundaries

- Customer reads: authenticated customer only, own active order and own history/credits. No cross-customer disclosure.
- Teammate queue and active-order RPCs: fresh teammate role, linked verified Discord, not suspended. Regular teammates see only approved games and never GG. GG teammates see only GG across games. Exclude prior rerolled teammates and own customer orders. Priority release is enforced on the server; never return priority values, hidden counts, customer UUID/payment/EUR total, queue timestamps/deadlines, previous assignments or private evidence.
- Accept: authenticate and validate eligibility, serialize per teammate and lock the order, check specific order expiry after locking, then conditional transition. Exactly one winner; already taken409, cancelled/expired410, busy409, ineligible/unreleased404 with no order payload. No caller-supplied bypass flag.
- Expiry: five minutes from initial queueing or reroll. A pre-read/pre-command sweep and specific locked-row check prevent acceptance after deadline. Expiry/cancel and refund posting commit together. Return structured business errors instead of raising after a mutation that must persist. A service-only bounded expiry-sweep RPC supports a scheduler; parent discovers available free scheduler before activation.
- Customer cancel: own queued order only. Cannot cancel accepted order. Repeated commands do not double-credit.
- Reroll: own in-progress order, at most twice and within first five minutes after accept; retain old assignment and exclude old teammate; reset queued timestamp and assignment. No new payment/refund event.
- Completion is deliberately unavailable until private proof authorization and durable earnings ledger are built. No pretend-completed actions. Admin handover, moderation, tips, presence/miss recording, realtime subscriptions and full admin mutation APIs remain subsequent slices. Do not fabricate missed-order penalties without qualified presence/visibility history.
- All functions fully qualify objects, use fixed empty search_path when SECURITY DEFINER, explicitly revoke PUBLIC/anon access, and derive actor from auth.uid. Validate grants/RLS/column restrictions and business errors using real role-switched SQL and two concurrent sessions.
